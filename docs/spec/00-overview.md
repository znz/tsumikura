# つみくら 概要

> 家庭用消耗品在庫管理 Web アプリ
> 表示名: **つみくら** / キャッチコピー: **家族でつなぐ、暮らしのストック**

## 1. 名前

- 表示は常にひらがなで **つみくら**。英字表記 (リポジトリ名・アプリ名) は `tsumikura`。
- 由来は 2 つの読みを重ねたもの。
  - **積み倉** — 家の中にある「積んである倉」。ストックそのもの。
  - **積み暮ら(し)** — 日々の暮らしを積み重ねる。買って、使って、また買う繰り返し。
- キャッチコピーは **家族でつなぐ、暮らしのストック**。「誰が使ったか / 誰が買ったか」を家族で引き継ぐことを表す。

## 2. スコープ

- **1 インスタンス = 1 世帯**。テナント分離は行わない (全データが単一世帯に属する)。
- 公開サインアップなし。最初の管理者は rake タスクで作成し、以降は管理者が画面から家族を追加する。
- **スマホファースト**。「使った」を 1〜2 タップで記録できることを最優先の UX 目標とする。
- UI は日本語のみ (`:ja`)、タイムゾーンは `Asia/Tokyo`。
- 在庫数は**整数**で管理する。小数・残量 (「洗剤 0.5 本」) は扱わない。
- v1 でやらないこと: JAN バーコードスキャン、品目写真、メール・チャット通知、複数世帯、用途別の次回交換予測、通知時刻の画面設定。

## 3. 確定要件

以下の表が仕様全体の基準となる。

| 項目 | 決定 |
|---|---|
| 利用範囲 | 自分の家族のみ。1 インスタンス = 1 世帯。テナントモデルなし |
| 運用 | 既存 Dokku に同居。Dockerfile デプロイ + 単一 `DATABASE_URL` + `SOLID_QUEUE_IN_PUMA` (コンテナ 1 つ)。Kamal は削除 |
| リアルタイム同期 | 不要。**Solid Cable は削除**。即時反映は HTTP レスポンスの Turbo Stream で行う |
| デバイス | スマホ中心。「使った」を 1〜2 タップで記録 |
| 通知 | ダッシュボード表示 + Web Push (PWA)。メール・チャットは使わない |
| 在庫単位 | 品目ごとに単位を持ち、整数で管理。購入は「入数 × パック数」または直接数量 |
| 使用開始 | 記録時点で在庫から引く (在庫 = 未使用数)。使い切り品も同じ操作。過去日の入力可 (未来日は不可) |
| 用途 | 品目ごとに用途を登録し、使用記録で用途と数量を選択。予測は品目全体。用途別には交換履歴と交換周期 (中央値) を表示 |
| 期限 | ロット (購入) ごとに期限 (任意)。使用時は FEFO 自動引当 (手動選択可)。期限切れ・期限間近の表示と廃棄の記録 |
| 認証 | Rails 8 標準認証ジェネレータ + パスキー (webauthn gem)。**ログイン ID はメールアドレス**。パスワードは常に必須 (パスキーは追加手段) |
| ユーザー管理 | 公開サインアップなし。最初の管理者は rake タスク、以降は管理者が画面から追加。管理者 / 一般の 2 段階。全記録に入力者を残す。パスワード忘れは管理者が再設定 |
| 要購入判定 | 予測の 3 段階 (購入不要 / そろそろ購入 / 購入推奨) + 最低在庫数 (任意)。悪い方を採用 |
| 棚卸差分 | マイナス差分は消費として予測に反映。廃棄とプラス差分は含めない |
| 追加機能 | カテゴリ・保管場所 / 買い物リスト / 価格 (税込合計)・購入店 |
| 技術 | RSpec + factory_bot (t_wada 流 TDD) / Tailwind CSS (tailwindcss-rails) / 日本語のみ (`:ja`) / `Asia/Tokyo` |

未確定なのは **Thruster を残すかどうか** (Dokku 初回デプロイ時に決める) など少数のみ。[未決事項](../plan/open-questions.md) を参照。

## 4. 用語

| 用語 | 英語 | 定義 |
|---|---|---|
| 品目 | Item | 管理対象の消耗品 (トイレットペーパー、単 3 電池) |
| ロット | Lot | 1 回の購入 (または初期在庫・棚卸調整) で入ってきた同一条件のかたまり。期限を持てる |
| 在庫移動 | StockMovement | 在庫の増減 1 行 (符号付き数量)。**在庫の唯一の真実** |
| 使用記録 | UsageRecord | 「使い始めた / 使った」というユーザー操作 1 回 |
| 用途 | ItemPurpose | 品目内の使い先 (リモコン、時計、体重計) |
| 棚卸 | StockTake | ある時点の実数を数えて記録在庫を合わせる操作 |
| 消費 | — | 在庫が「使われて」減ること。使用 (`usage`) と棚卸のマイナス差分 (`adjustment` かつ負) を指す。廃棄は含まない |
| 消費イベント | — | 消費のあった日。同じ日の複数の記録は 1 件と数える |
| 消費ペース | Pace | 1 日あたりの消費量 (個/日) |
| アンカー | anchor | 最後の消費イベント日 (無ければ最初の在庫イベント日)。在庫切れ予測日の起点 |
| 在庫切れ予測日 | need_by_on | 「次に使いたいときに未使用在庫が無い日」。詳細は [予測と要購入判定](02-forecast.md) |

## 5. 設計原則

1. **在庫は台帳から導出する。** `stock_movements` の符号付き数量の総和が唯一の定義。集計列はすべて再計算可能なキャッシュとする。
2. **残数計算は順序非依存にする。** 日付順の再生をしないので、過去日付の記録を後から足しても現在庫は壊れない。
3. **記録は必ず成功させる。** 在庫不足でも「使った」は記録できる (不足分は自動で調整ロットを作る)。エラーで家族の入力意欲を削がない。
4. **予測は参考値。** 3 段階の目安と最低在庫数の 2 系統を持ち、悪い方を採用する。データ不足時は黙る (`unknown`)。
5. **ドメインロジックは PORO。** 予測計算は ActiveRecord 非依存の純粋関数にして、DB なしで高速にテストする。
6. **通知はうるさくしない。** 即時通知はせず、1 日 1 回のダイジェストのみ。しかも状態が悪化したときだけ送る。

## 6. 将来の拡張候補 (v1 スコープ外)

| 候補 | 備考 |
|---|---|
| JAN バーコードスキャンでの品目登録 | 今はスキーマに `jan_code` も持たない。必要になったら migration 1 本で足す |
| 品目の写真 | Active Storage + 永続ストレージ。マウントだけ先に用意する ([デプロイ](../ops/deployment.md)) |
| メール・チャット通知 | v1 はメール送信手段を持たない (パスワード再設定も管理者操作) |
| 複数世帯 (マルチテナント) | 現在は全データが単一世帯前提 |
| 用途別の次回交換予測 | v1 は用途別には履歴と交換周期の表示のみ |
| 小数・残量管理 (「洗剤 0.5 本」) | `decimal(10,2)` への移行で対応可能 |
| 通知時刻の画面設定 | v1 は `config/recurring.yml` の書き換え + 再デプロイ |
| 消費ペースの直近重視 (二段窓など) | 予測が PORO なので、運用してみて追随が悪ければ差し替える |
